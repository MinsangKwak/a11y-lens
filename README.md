# a11y-lens

배포된 웹사이트의 **명암비와 웹 접근성을 검사하는 데스크톱 도구**입니다.
외주 산출물 검수를 염두에 두고 만들었습니다 — 검사 결과가 그대로 수정 요청 근거가 되어야 합니다.

![공통 판정 엔진과 CLI · 데스크톱 · 명암비 이력 대조의 구조](docs/assets/architecture.png)

구조를 설명하는 그림입니다. 실제 Electron 실행 화면이 아니며, 그 확인은 아직 남아 있습니다.

[진행 현황과 남은 일](docs/PROGRESS.md) · [CI 구조와 실측 결과](docs/CI.md) · [검증 기록](docs/VALIDATION.md) · [브랜치 보호 적용안](docs/BRANCH_PROTECTION.md)

## 왜 데스크톱인가

웹 서비스로 만들 수도 있었지만 세 가지가 걸립니다.

1. **남의 사이트를 서버에서 긁지 않는다.** 서버가 외부 사이트에 요청을 보내면 부하 · 차단 · 책임이 운영자에게 옵니다. 검사를 사용자 기기에서 돌리면 그 문제가 없습니다.
2. **로그인 상태를 검사할 수 있다.** 관리자 화면, 결제 완료 페이지처럼 세션이 필요한 자리는 서버 크롤러가 못 갑니다.
3. **고객사 화면이 서버에 남지 않는다.** 검사는 기기에서 돌고, 계정에 올라가는 것은 수치와 선택자뿐입니다. 화면 캡처는 로컬에만 둡니다.

브라우저 익스텐션도 검토했지만, **URL 목록 배치 실행**과 **검사 이력 비교**가 안 됩니다.
외주 검수의 본질은 "1차에 지적한 12건 중 9건이 수정됨"을 자동으로 내는 것이고, 그게 익스텐션으로는 불가능합니다.

## 구조

```
packages/
  core/      판정 엔진 + axe 어댑터 + 이력 대조. 의존성 0
  desktop/   Electron 셸 + React 렌더러 + 계정
  cli/       같은 엔진을 Playwright 로 배치 실행 — CI 에 붙이는 길
db/
  schema.sql 계정별 이력. RLS 로 격리
```

`core` 를 플랫폼 독립으로 떼어 둔 이유는 **잣대가 두 벌이 되지 않게** 하기 위해서입니다.
데스크톱과 CLI 가 각자 판정 로직을 가지면, 예외 하나를 더할 때 한쪽에만 들어갑니다.

엔진은 소스로 직렬화되어 대상 페이지 안에서 돕니다.

| 셸 | 주입 방법 |
| --- | --- |
| Electron | `webContents.executeJavaScriptInIsolatedWorld(999, [{ code }])` |
| CLI | `page.evaluate(AUDIT, options)` |

접근성 규칙도 같은 길로 갑니다. 셸이 axe-core 소스를 먼저 넣고, 같은 월드에서 `RUN_AXE` 를 돌립니다.
**axe-core 패키지는 셸의 의존성입니다** — `core` 는 의존성 0 을 지켜야 하므로 라이브러리를 품지 않고
규칙 선별과 결과 정규화만 들고 있습니다.

격리 월드를 쓰는 이유는 **대상 페이지의 CSP 가 스크립트 주입을 막는 경우**가 있기 때문입니다.
일반 `executeJavaScript` 는 그런 사이트에서 실패합니다.

## 판단 기록

구현에서 선택이 갈렸던 자리와 그 이유입니다.

### 기준값을 하드코딩하지 않았다

WCAG 2.1 AA 는 본문 4.5, 큰 글씨 3.0 입니다. 그런데 자체 서비스의 회귀 검사에는 3.0 단일 기준이 더 맞습니다 —
거기서 찾으려는 건 "읽기 불편함" 이 아니라 **"아예 안 보임"** 이고, 기준을 올리면 고칠 수 없는 색까지 매번 빨개져서
아무도 결과를 보지 않게 됩니다. 울다 지친 경보는 경보가 아닙니다.

그래서 기준은 호출하는 쪽이 넣습니다. 같은 엔진이 두 잣대를 섬깁니다.

### 잴 수 없는 것을 통과시키지 않았다

배경에 그림이나 그라데이션이 깔리면 바탕을 단일 색으로 환산할 수 없습니다.
초기 구현은 이 경우를 그냥 건너뛰었는데, **히어로 · 배너가 전부 여기 해당합니다** — 글자가 가장 크고 중요한 자리입니다.

지금은 `undeterminable` 로 **보고**합니다. 추측한 수치를 내는 것보다, 사람이 볼 목록으로 넘기는 쪽이 안전합니다.
틀린 통과는 미검출보다 나쁩니다.

### 보고서에 "보이는 색" 을 적는다

`opacity: .3` 이 걸린 검은 글자는 선언상 `#000` 이지만 실제로는 `rgb(179,179,179)` 로 보입니다.
선언값을 적으면 "검정 글씨인데 왜 미달이냐" 는 반박이 돌아옵니다. 합성까지 끝낸 색을 적습니다.

조상의 `opacity` 는 글자에만 누적합니다. 바탕을 준 조상의 `opacity` 는 글자와 바탕을 함께 흐리므로
명암비를 바꾸지 않습니다.

### 로그인 게이트는 보안 장치가 아니다

데스크톱 앱의 검증 분기는 우회됩니다. 코드가 사용자 기기에 있기 때문입니다.
그래서 "로그인한 사람만 쓰게" 를 `if` 로 풀지 않았습니다.

대신 **가치를 서버에 두었습니다.** 검사 이력과 1차 · 2차 대조가 계정에 있으므로,
로그인하지 않으면 한 번 재고 끝입니다 — 외주 검수에 쓸 수 없습니다.
격리는 앱이 아니라 RLS 가 서버에서 지킵니다. 앱이 `WHERE` 절을 빠뜨려도 남의 줄은 보이지 않습니다.

`SUPABASE_ANON_KEY` 는 공개 브라우저 식별자이고 서버 비밀이 아닙니다. 둘을 혼동하면
"키를 숨겼으니 안전하다" 는 잘못된 안심에 빠집니다.

### 토큰은 OS 키체인에 둔다

`localStorage` 는 평문이고 렌더러에서 읽힙니다. Electron 의 `safeStorage`(macOS Keychain ·
Windows DPAPI)로 봉해 메인 프로세스만 들고 있고, 렌더러에는 **토큰을 주지 않고 신원만** 보냅니다.

OAuth 창은 시스템 브라우저로 엽니다. 앱 안의 창으로 열면 Google 이 막습니다(`disallowed_useragent`).

### 같은 자리를 알아보는 열쇠는 선택자다

이력 대조에서 "같은 결함인가" 를 가릴 때 색을 열쇠에 넣으면, 외주사가 색을 고친 순간
**1건 해결 + 1건 신규**가 되어 수정한 사람을 벌주는 보고서가 나옵니다.
선택자만 봅니다. 구조가 개편되어 선택자가 바뀌면 신규로 잡히는 게 맞습니다 — 자리가 옮겨졌으면 다시 봐야 합니다.

합의된 예외(`allowed`)는 양쪽에서 빼고 셉니다. 고치지 않기로 한 것을 미해결로 세면
보고서의 숫자가 영원히 줄지 않습니다.

### 접근성 규칙은 빌려 쓰고, 골라서 켠다

규칙을 직접 쓰지 않고 axe-core 를 어댑터로 붙였습니다. 접근성 규칙은 판정 경계가 많고
그 경계가 ARIA 명세와 함께 움직입니다. 직접 쓰면 유지가 안 되고, **틀린 지적 한 건이 보고서 전체의
신뢰를 깎습니다.**

전체(105개)를 돌리지 않고 **60개만 켭니다.** 고르는 기준은 셋입니다 — WCAG A·AA 에 걸릴 것,
수정 요청으로 바로 옮길 수 있을 것, 거짓 양성이 드물 것. `best-practice` · `experimental` · AAA 는 전부 뺐습니다.
전부 켜면 "이론상 위반" 이 수십 건 나오고, 그런 보고서는 아무도 읽지 않습니다.

`color-contrast` 는 **끕니다.** 자작 엔진이 같은 것을 재는데 기준값이 설정으로 움직이므로(4.5 대 설정값),
둘을 함께 켜면 같은 자리에 다른 수치가 두 번 적힌 보고서가 나갑니다.
무엇을 껐는지는 `AXE_SKIPPED` 에 이유와 함께 적어 두었고, JSON 보고서에도 함께 나갑니다 —
**무엇을 보지 않았는지 모르면 "검사했다" 는 말이 과장이 됩니다.**

axe 의 `incomplete`(판단 불가)는 버리지 않고 `undeterminable` 로 넘깁니다. 명암비 쪽과 같은 어휘를 쓰는 이유는
보고서에 두 결과가 나란히 들어가기 때문입니다. 이력 대조의 열쇠는 **규칙 + 자리**입니다 —
선택자만 쓰면 한 자리에 걸린 서로 다른 규칙을 한 건으로 뭉갭니다.

### 큰 글씨 분기가 없으면 보고서를 못 쓴다

24px, 또는 18.66px 굵게는 기준이 3.0 입니다. 이 분기가 빠지면 **정당하게 통과한 제목을 전부 위반으로 잡습니다.**
한 번 그런 보고서를 보내면 다음 보고서도 안 읽힙니다.

## 검사 범위의 한계

자동 검사는 접근성 위반의 일부만 잡습니다. 이 도구는 **사람이 볼 자리를 좁혀 주는 도구**이지 판정기가 아닙니다.

자동으로 잡히지 않아 수동 확인이 필요한 것:

- 키보드만으로 전체 조작 — 탭 순서, 포커스 표시, 모달 포커스 가둠과 탈출 (초점이 갇히는 자리 일부는 규칙이 잡습니다)
- `alt` 텍스트의 **내용** 적절성 (존재 여부는 잡습니다)
- 동적 변화가 스크린리더에 전달되는지 (`aria-live`)
- 확대 200% 에서 레이아웃이 깨지지 않는지
- 배경 그림 위 글자 — `undeterminable` 목록으로 뽑아 줍니다
- 일부러 끈 규칙 — 조작 영역 크기(`target-size`), 제목 단계 건너뛰기(`heading-order`), 본문 속 링크 구분(`link-in-text-block`)

웹접근성 품질인증(과기정통부)은 전문가 심사와 사용자 심사를 포함합니다.
**이 도구의 통과는 인증 가능을 뜻하지 않습니다.**

## 쓰는 법

```bash
pnpm install
cp .env.example .env          # Supabase 주소 · 공개 키 (MAIN_VITE_ 접두사 필요)
psql "$DATABASE_URL" -f db/schema.sql

pnpm test                          # core 엔진 + CLI·데스크톱 검사 흐름 회귀
pnpm dev                           # 데스크톱 앱
pnpm scan -- https://example.com   # CLI 로 한 장 (계정 없이 동작)
```

CLI 는 명암비와 접근성 규칙을 함께 돌립니다. 규칙을 빼려면 `--no-axe`,
일부만 켜려면 `--axe-rules image-alt,label`, 고치지 않기로 합의한 규칙은 `--axe-allow bypass` 입니다.

CLI 는 계정을 쓰지 않습니다. CI 에서 돌리는 자리이고, 거기서 필요한 것은 이력이 아니라 종료코드입니다.

- 종료코드 `0`: 요청한 검사를 완료했고 기준 미달을 찾지 않았습니다. 사람이 볼 항목은 별도로 남습니다.
- 종료코드 `1`: 검사를 완료했고 기준 미달을 찾았습니다.
- 종료코드 `2`: URL 이동·명암비·접근성 검사 중 하나가 실패했거나 사용법이 잘못됐습니다.
- JSON의 각 페이지에 `status`(`complete`·`partial`·`failed`)와 `errors`(단계·메시지)를 기록합니다.
  접근성 검사 실패 또는 `--no-axe` 사용 시 `axe`는 `null`입니다. 의도한 생략 여부는 `options.axe`로 구별합니다.
  접근성만 실패해도 명암비 결과는 보존하지만 전체 검사는 성공 종료하지 않습니다.

데스크톱의 “이 화면 검사”도 명암비와 접근성 규칙을 함께 실행하며, 위반과 사람이 볼 항목을 나눠 보여 줍니다.
어느 검사든 실행에 실패하면 이전 결과를 지우고 실패를 표시합니다. **이력 저장과 지난 검사 대조는 명암비만 포함합니다.**
접근성 결과의 HTML과 실패 사유는 서버에 보내지 않습니다.

셸 회귀는 CLI의 실패·부분 실패·다중 URL·예외 규칙·규칙 생략과 데스크톱의 두 엔진 연결·실패 전파를 확인합니다.
데스크톱 자동 회귀는 Electron 창을 띄우지 않습니다. 실제 격리 월드 주입과 화면 표시는 별도 GUI 확인이 필요합니다.

전체 검증은 `pnpm verify`로 실행합니다. 전체 빌드와 타입 검사 뒤에 기존 테스트 43건을 실행하며, 같은 산출물을 다시 빌드하지 않습니다. CI의 실행 조건과 시간 비교는 [CI 검증 구조](docs/CI.md)에서 확인할 수 있습니다.
